# Lung

What do updating stored lung query analyses to a revised reference and rerunning sensitivity configurations on their stored results cost, against a complete rerun?

Run: each Modal job is `uv run --group cloud python -m experiments.modal_runner run MODULE FUNCTION payload.json`, with `--cpu` and `--memory-gib` matching the payload's `containerCpu` and `containerMemoryMb` where it names them. `build_plan` in `lung_pipeline`, `reference_revision` and `lung_robustness` returns the payloads of their jobs from the bucket's results and datasets roots. Payloads give the bucket endpoint as `r2EndpointUrl` and bucket locations as `s3://` URIs, and every job writes its record to the payload's `recordUri`. In order:

1. Reference screen, the stored analyses that the update and the sensitivity runs start from: `lung.lung_pipeline` `convert_job` for `hlca_core`, `hlca_full` and `natri_ild`, then `map_job` and `characterise_job`. `uv run --locked python -m experiments.lung.collect_lung` collects their records into `$CYTEARC_RUNS/lung/results/`, and `uv run --locked python -m experiments.lung.lung_analysis --data $CYTEARC_RUNS/lung/results` summarises them into `.build/derived/lung/lung_reference_screen_summary.json`.
2. Reference update: `lung.reference_revision` with each job of `build_plan(...)["jobs"]`, which names its function and payload, in the order of `phases`: the revised reference and the five query stores, the Natri update, the complete Natri rerun, the four other updates, and the stats. `uv run --locked python -m experiments.lung.collect_revision fetch` writes `lung_reference_update_summary.json`, `lung_reference_update_records.json` and `lung_reference_update_costs.csv` into `records/`; it also writes per-store label tables and cell exports, which the paper does not use.
3. Sensitivity: `lung.lung_robustness` `references_job`, `extended_mount_job` with the `extended` payload, `extended_reference_job`, `query_job` with `query_projection`, `query_references` and `query_extended`, and `analysis_job` with `analysis` and `check`. Both check the primary configuration against the screen run's findings, so their payloads come from `build_plan(..., screen_findings=lung_robustness.screen_findings(summary))`, where `summary` is the screen summary of step 1. `uv run --locked python -m experiments.lung.collect_robustness` writes `lung_sensitivity_costs.csv` and `lung_sensitivity_records.json` into `records/`; it also writes the run's summary, outcomes and cluster assignments, which the paper does not use.

Needs: no other experiment; the core and full Human Lung Cell Atlas and the Natri ILD cohort from CELLxGENE, at the versions that `lung_pipeline.DATASETS` pins, each staged in the bucket under `datasets_root` as `biocase/<name>.h5ad` with a `biocase/<name>.json` record of its `datasetVersionId` and `sourceSha256`; and the bucket and folder variables that `experiments/README.md` lists.

Records:

- `lung_reference_update_summary.json`: five query stores updated from the core atlas to a reference that adds the Kaminski_2020 cells with the authors' aberrant basaloid label; per store, the label changes, unexplained cells, costs and exact recovery of the first version's results; and the Natri update against a complete rerun of both versions in a fresh store.
- `lung_reference_update_costs.csv`: one row per step of each job of the update, from the revised reference and the five query stores to their updates and the complete Natri rerun: seconds, bytes read from the core atlas, the full atlas, the Natri store and the revised reference, bytes received over the network, peak resident memory and bytes added, with the artifact the step created or found stored.
- `lung_reference_update_records.json`: the record of each job of the update.
- `lung_sensitivity_costs.csv`: seconds, bytes added and artifacts computed and reused for the primary configuration and its 10 one-setting variations.
- `lung_sensitivity_records.json`: the record of each job of the sensitivity runs.
